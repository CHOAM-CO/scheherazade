**Findings**

- High: Invalid Claude subscription tokens are accepted as “connected” and stored. In [http-server.cjs](/Users/narr/Desktop/scheherazade/onboarding/http-server.cjs:855), `claude-subscription` validation only checks non-empty input and returns `{ ok: true }`; then [http-server.cjs](/Users/narr/Desktop/scheherazade/onboarding/http-server.cjs:1110) stores it. A typo or pasted wrong value gets a success screen in Step 1, then fails much later at agent spawn after the user has already completed Discord setup.

- High: Discord routes to the wrong server/channel for users with existing Discord history. [http-server.cjs](/Users/narr/Desktop/scheherazade/onboarding/http-server.cjs:921) chooses `guilds[0]`, then [http-server.cjs](/Users/narr/Desktop/scheherazade/onboarding/http-server.cjs:933) chooses the first text channel by position. The tutorial tells the user to invite the bot to a server they selected, but the app never asks which one and does not verify recency or intended guild. A user with multiple bot guilds can finish onboarding and be told the agent is in `#channelName`, while it is actually wired to some unrelated first guild/channel.

- Medium: The subscription-token UI uses API-key failure/status copy. [wizard.js](/Users/narr/Desktop/scheherazade/onboarding/public/js/wizard.js:261) explicitly reuses `C.step1.fallback.validating/success/failure`; [wizard.js](/Users/narr/Desktop/scheherazade/onboarding/public/js/wizard.js:277) renders “키가 거부됐습니다” for setup-token failures. For the primary Claude subscription mode this misleads non-technical users into debugging an API key they never used.

- Medium: Step 5 sends users to a dead recovery path. Failure copy says “설정에서 모델 키와 인증 정보를 확인” for `crash_loop`/`key_error` in [copy.js](/Users/narr/Desktop/scheherazade/onboarding/public/js/copy.js:249), and [wizard.js](/Users/narr/Desktop/scheherazade/onboarding/public/js/wizard.js:613) wires `openSettings`; but settings only supports rename plus a Slack placeholder in [settings.js](/Users/narr/Desktop/scheherazade/onboarding/public/js/settings.js:34). There is no model/key/token repair UI, so the recommended action cannot fix the failure.

- Medium/security: The localhost auth token can be read by any local process that finds the ephemeral port. The server injects `SERVER_TOKEN` into every served HTML page at [http-server.cjs](/Users/narr/Desktop/scheherazade/onboarding/http-server.cjs:1053), while GETs are not token-gated and the token is only checked for POST/DELETE at [http-server.cjs](/Users/narr/Desktop/scheherazade/onboarding/http-server.cjs:1379). That weakens the stated “any other local process” protection: a local process can GET `/`, extract the meta token, then call mutating APIs.

- Low: “나중에 하기” / interrupted onboarding does not resume from saved progress except through `/waiting`. The server saves `ONBOARDING_STEP: '3'` at [http-server.cjs](/Users/narr/Desktop/scheherazade/onboarding/http-server.cjs:1197), but wizard init only honors `?step=4` at [wizard.js](/Users/narr/Desktop/scheherazade/onboarding/public/js/wizard.js:711) and otherwise always shows Step 0 at [wizard.js](/Users/narr/Desktop/scheherazade/onboarding/public/js/wizard.js:721). A quit/reopen after provider/persona setup makes the user start over.
